# 微信小游戏资源方案（先玩法，后接入）

本文档用于沉淀当前项目在微信小游戏场景下的资源管理方案。当前策略为：先完成玩法闭环，资源热更系统在后续阶段接入。

## 1. 阶段策略

- 当前阶段：优先玩法开发，不让资源系统改造阻塞迭代。
- 过渡约束 1：资源访问建议统一通过抽象层（例如 `IAssetProvider`），先接本地实现，后续再切 `YooAsset`。
- 过渡约束 2：资源从现在开始按固定命名/分组规范组织，避免后期大规模迁移。

## 2. 技术选型

- 资源框架：`YooAsset`（后续接入）。
- 远端托管：腾讯云 COS + CDN（或等价国内 CDN）。
- 发布策略：按 `Package` + `Tag/Label` 输出版本清单与资源包。

说明：`YooAsset` 不是只靠命名生效，核心依赖构建配置；命名规范用于让配置可读、可批量维护、降低误配风险。

## 3. 分组与分包策略

建议统一使用以下分组前缀：

- `base_`：首包必需资源（开局必须可用）
- `feature_`：玩法功能资源（按模块按需下载）
- `event_`：活动资源（可独立上下线）
- `audio_`：音频资源（通常体积大，独立管理）

推荐示例：

- `base_core`：启动场景、基础 UI、字体、通用材质
- `base_map`：基础地图资源（含 TileDatabase 与基础草地变体）
- `feature_combat` / `feature_shop`：玩法模块资源
- `event_spring2026`：活动期资源
- `audio_bgm_main`：背景音乐包

## 4. 当前项目落地映射

### 4.1 地图生成链路

`TilemapManager` 当前生成优先级：

1. 特殊遭遇模板（`encounterRegistry`）
2. 程序化生成（`proceduralGenerator`）
3. 随机模板回退（`useTemplateFallback`）

可见代码：`Assets/Script/Managers/TilemapManager.cs`

### 4.2 草地变体方案

当前草地采用 `ProceduralChunkGenerator` 方案：

- 主噪声选地形段
- 副噪声在 `[baseTileId, baseTileId + grassVariantCount - 1]` 内选草地变体
- Tile id 写入后由 `TileDatabase.GetTileById()` 映射为实际 Tile

可见代码：

- `Assets/Script/Managers/ProceduralChunkGenerator.cs`
- `Assets/Script/Utilities/TileDatabase.cs`

注意：`TileDatabase` 的 id 从 1 开始，`id=0` 代表空。

## 5. 接入时机与实施步骤

当玩法核心闭环稳定后，再按以下顺序接入：

1. 建立 `YooAsset` 包配置与 Tag 规则
2. 按 `base_/feature_/event_/audio_` 完成资源分组
3. 接入启动检查更新与按需下载流程
4. 打通预发/正式 CDN 发布链路
5. 增加弱网、断网恢复与回滚验证

## 6. 验收目标（后续接入阶段）

- 首次进入主场景时长可控（按目标机型设定）
- 功能页按需下载成功率稳定
- 更新失败可重试且可回滚
- 资源改动只触发受影响分组更新，避免全量重下
