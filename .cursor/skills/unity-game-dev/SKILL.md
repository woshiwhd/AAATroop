# Unity 游戏开发规范

## 适用范围
本 Skill 适用于当前仓库的 Unity 开发流程。在修改玩法代码、管理器、地图生成、场景/预制体配置或资源驱动系统时应遵循本规范。

## 核心规则
1. 行为变更应最小化且明确，避免在同一任务中做无关重构。
2. 优先扩展现有 Manager 流程，再考虑新增全局系统。
3. 命名与项目既有术语保持一致，如 `Chunk`、`Tilemap`、`Generator`、`Registry`。
4. 保证 Unity 序列化安全（`[SerializeField]` 字段与资源引用）。
5. 修改组件脚本时，避免破坏场景或预制体上的引用关系。
6. 文档类产出必须放在 `Unity/Assets/Docs` 目录，不放在其他路径。

## C# 实现规范
1. 方法保持小而聚焦，命名清晰可读。
2. 对运行时加载资源与场景引用做好空值保护。
3. 公共 API 面尽量小，默认优先使用 `private` 或 `internal`。
4. 仅在非直观逻辑处添加简洁注释，例如生成规则、权重计算。
5. 接口与实现职责单一（例如：生成契约与具体算法分离）。

## 地图与程序化生成
1. 提供种子时，生成结果应可复现。
2. 纯生成决策与场景写入操作分离。
3. 避免无命名的魔法数字，提取为常量。
4. 写入地图数据前，校验 tile ID 或查找键是否合法。
5. 新增遭遇或 Chunk 规则时，提供兜底逻辑，避免生成空结果。

## 场景与预制体安全清单
- 确认脚本字段重命名不会破坏序列化数据。
- 组件依赖关系要明确（运行时必须能定位必需的 Manager）。
- 仅脚本改动时，避免大范围改写 Scene。
- 若涉及 Prefab/Scene 行为，需验证生成、移动、瓦片渲染初始化正常。

## 变更汇报格式
完成任务后按以下结构输出：
1. 改了什么
2. 为什么改
3. 做了哪些验证
4. 风险与后续建议

## 可选扩展
- 引入自动化测试后，补充项目专用测试命令。
- 若图集导入与瓦片批处理流程标准化，补充资源流水线说明。

## 文档放置规范
1. 新增或更新的项目文档，默认放在 `Unity/Assets/Docs`。
2. 文档索引需同步更新 `Unity/Assets/Docs/README.md`。
3. 文档命名使用清晰中文标题，避免 `new-doc`、`temp` 等临时命名。
